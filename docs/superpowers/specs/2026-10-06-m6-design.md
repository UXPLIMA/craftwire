## 1. Multi-version agents

**Facts (2026-10-06).** 26.3 is released (2026-09-15); Paper 26.3 has beta builds only; 26.4 is in snapshots.
26.3 replaced GLFW with SDL3 (and added Vulkan). Compiling the agents against 26.3 breaks in six places:
Fabric's F8 kill switch, key/modifier codes in `gui_action type`, the hidden-window mixin; Paper's bot
teleport-accept packet, the swing packet and the player-chat packet accessors.

**Decision: one jar per loader that runs on every supported version.**
- `agent-fabric` and `agent-paper` keep the common code, compiled against the oldest supported version (26.2).
  Since 26.x is unobfuscated, common code that only touches members unchanged across versions runs as-is.
- Anything that differs goes behind a small interface in the common code (`Compat`), implemented once per
  version in `agent-fabric/compat/<mc>` and `agent-paper/compat/<mc>` (Gradle projects compiled against that
  version). The jar bundles every implementation; at startup the agent picks the one for the running
  version (exact match, else the newest one not newer than the game) and logs which.
- Version-specific mixins live in the compat projects and are applied only on their version through a mixin
  config plugin (`shouldApplyMixin`).
- Version data lives in `versions/<mc>.properties` (Minecraft, Fabric API, Paper dev bundle, Paper build and
  sha256). Adding 26.4 = one properties file + one compat project per loader if something broke.
- Tests: the same built jars are tested on every version. Paper ITs take `-Pmc=<version>` and download that
  Paper build. Client game tests run from a per-version Loom project (`agent-fabric/gametest/<mc>`) that loads
  the built agent jar. CI runs the matrix.
- Hub: `client_process` takes `version` (default: newest supported release); pins per version.

**Rejected.** Per-version jars (users must pick, hub must match); reflection for the differences (no type
checking, silent breakage); Stonecutter (third-party build plugin, preprocessor comments in source).

## 2. Events and exceptions

**Events (Paper).** A recorder registers one MONITOR-priority executor on every `HandlerList` (and on lists
created later, re-scanned when a plugin enables). It records each event with time, type, the player/entity
involved, `cancelled` and a shallow field snapshot (getters returning primitives, strings, enums, locations,
item types; depth 1; truncated). High-rate events (`*MoveEvent`, physics, chunk load, entity tick-like)
are counted but not stored unless asked (`capture` list). Ring buffer, 5000 events.

Tool `events`:
- `summary {since?, window?}`: counts per type (+ cancelled counts).
- `query {type?, player?, since?, limit?, cancelledOnly?}`: individual events.
- `listeners {type}`: who listens to an event: plugin, priority, ignoreCancelled, listener class. This answers
  "is my listener even registered?".

**Exceptions (hub, both agents).** The hub already receives log lines with folded stacks. It groups errors by
signature (exception class + top in-project frames, message digits normalised), keeps count, first/last seen,
the instance, and attributes them to a plugin/mod by package/frames. Tool `exceptions {since?, instance?}` lists
groups; `{id}` returns one full stack. Works for clients and servers alike.

## 3. Richer `wait_for`

Existing event conditions stay. New server-side conditions are evaluated by the Paper agent every tick
until true or timeout (no polling from the hub):
- `block {x,y,z, is? | isNot?}` (id or state string),
- `player_near {player, x,y,z, radius}` (bots included),
- `inventory {player, item, count?}`,
- `event {type, player?, match?}` (from the event recorder; only events after the call),
- `expr {js}`: a `server_eval` expression that must become truthy (only when eval is allowed).
The result says which condition held and how long it took; on timeout it returns the last observed value.

## 4. Scenarios

A scenario is a list of steps run by the hub, so a step can be any Craftwire tool call:
`{tool, args}` plus sugar (`bot`, `command`, `wait`, `expect`). Assertions:
`expect {tool, args, path, equals|matches|contains|exists|lessThan|greaterThan}` evaluated on the tool result
(path syntax `a.b[0].c`, with `[*]` "any element"). Built-in shortcuts: `expect_message {bot, matches}`,
`expect_hud`, `expect_block`, `expect_event`, `expect_no_exceptions`.
On failure the run stops and returns: the failing step, expected vs actual, and context gathered at that moment
(bot messages and HUD, events since the scenario started, new exception groups, last log lines).
`setup`/`cleanup` blocks always run cleanup.

- MCP tool `scenario_run {scenario | file}`.
- CLI `npx craftwire test [files…] [--server <dir>]`: starts a hub, optionally starts the Paper server via the
  same code as `server_process`, runs the files (`*.cwtest.json`), prints a report, exits non-zero on failure
  (JUnit XML with `--junit <file>` for CI).

## 5. Extension API

Plugins and mods register tools that show up in MCP as `<namespace>_<name>`.
- `craftwire-api` (new Gradle module, Java 21, no dependencies): `CraftwireTool` (name, description, JSON
  schema string, `handle(String jsonArgs) -> String json`), `Craftwire.registry()` lookup.
- Paper: exposed through Bukkit's `ServicesManager`; plugins `softdepend: [Craftwire]`.
- Fabric: entrypoint `"craftwire"` in `fabric.mod.json`; Craftwire calls it with the registry.
- The agent announces its extension tools to the hub (`tools.changed`); the hub registers/unregisters them and
  sends `notifications/tools/list_changed`. Calls are forwarded like any other request, on the game thread
  unless the tool says otherwise. Errors become normal Craftwire errors.
- Published as a jar on each GitHub release and through JitPack.

## 6. `world_render` (Paper)

PNG of a region without any client:
- `top`: the surface seen from above, coloured like vanilla maps (map colours, height shading, water depth).
- `slice {y}`: a horizontal cut; `side {facing}`: an elevation (front view) of the region.
- Optional grid every N blocks and coordinate labels at the edges, so the image can be talked about in
  coordinates. Max 512×512 blocks; `scale` pixels per block (1–8).

## 7. Singleplayer worlds for `client_process`

`client_process start {world: {name, create?: {type: flat|normal|void, seed?, gameMode?, cheats?}}}` instead
of `server`. The agent creates the world (vanilla world-creation path) or opens an existing one with quick play.
Client tools work as usual; `instance` is the client.

## 8. Remote HTTP mode

`npx craftwire serve [--port 7777] [--host 127.0.0.1] [--allow-remote] [--tls-cert --tls-key]`.
- MCP Streamable HTTP at `/mcp`; one hub process serves several MCP clients at once.
- Bearer token always required (stored in `~/.craftwire/http.json`, rotate with `--rotate-token`), compared in
  constant time; `?token=` is not accepted.
- Binding a non-loopback address requires `--allow-remote`; without TLS it prints that the token travels in
  clear text and suggests TLS or an SSH tunnel.
- DNS-rebinding protection: `Host` must match the bound host/allowed hosts; requests with an `Origin` header are
  rejected unless the origin is allow-listed.
- Per-token rate limit (default 120 requests/min), request size limit, idle session expiry.
- `--read-only` registers only tools that change nothing; `--tools <groups>` limits the tool surface.
- Agents still connect to the hub over the local WebSocket; nothing new is exposed on the game side.
