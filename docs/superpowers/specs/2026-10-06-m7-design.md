## 1. `profile` and `trace`

**Goal.** Answer "what eats the tick (or the frame), and which plugin or mod is it?" and "how often and how long
does this method run, and who calls it?" without a profiler install and without touching the code under test.

**Decision: JDK Flight Recorder, from inside the agent.** Minecraft 26.x needs Java 25+, and every Java 25 build
ships JFR. `jdk.ExecutionSample` (default every 10 ms) samples the game thread with low overhead and no
safepoint bias. JDK 25's `jdk.MethodTrace` / `jdk.MethodTiming` (JEP 520) instrument exactly the methods a filter
names, at runtime, and remove the instrumentation when the recording ends. No dependency, no Java agent, no
bytecode of ours in the game. Prototyped on JDK 26: both work from a `RecordingStream` started at runtime.

*As built:* `profile` does not use `jdk.ExecutionSample`. On a Paper server that mostly sleeps between ticks it
produced only a handful of samples per second (JFR samples only threads running Java code at that instant), too
few to name a plugin. `profile` samples the game thread itself with `ThreadMXBean.getThreadInfo` every
`intervalMs` and counts waiting samples as idle (`busyPercent`). `trace` uses JFR as designed (`jdk.MethodTiming`
with period `endChunk`, so the totals arrive before the recording stops).

**Owners.** Every stack frame is attributed to an owner:
- Paper: each plugin's jar is indexed once (class names in the jar, shaded libraries included, so a library a
  plugin bundles counts as the plugin). Then by package: `net.minecraft.` → minecraft; CraftBukkit, Paper,
  Spigot, Moonrise → server; `java.`, `jdk.`, `sun.` → java; Craftwire's own classes → craftwire.
- Fabric: each mod's origin (jar or, in development, a folder) is indexed the same way. Mixin handler methods
  carry the mod id in their name (`handler$…$modid$…`), so code a mod injected into Minecraft classes counts as
  that mod. Fabric Loader/API frames → their mods; the rest as on Paper.

**`profile {durationMs 1000-60000 (10000), intervalMs 5-50 (10), top 1-50 (15)}`** on a server or client
instance. Samples the game thread ("Server thread" / "Render thread"). Returns:
- `samples`, `durationMs`, `thread`.
- `owners`: each sample goes to the innermost frame owned by a plugin or mod (time a plugin spends inside
  Minecraft code it called counts as the plugin); with no plugin/mod frame, to the top frame's owner. Percent of
  samples per owner.
- `entryPoints`: per plugin/mod, its outermost frames (where the server called into it), with percent, the caller
  frame, and the kind when recognisable: an event listener (`event: PlayerMoveEvent`, from the method's parameter
  type) or a scheduler task.
- `hotMethods`: top self-time methods with their owner.
- Server: `ticks` from Paper's tick start/end events: count, MSPT average, p50, p95, max, ticks over 50 ms, and
  the 5 slowest ticks with the owners sampled during them. Client: `fps` (average, minimum).
The hub waits `durationMs` + 15 s.

**`trace {method, durationMs 1000-60000 (10000), minMs (0), stackDepth 1-32 (8), limit 1-200 (50)}`**:
`method` is `com.example.Shop::buy` (one method), `com.example.Shop` (every method of the class) or
`@com.example.Annotated` (methods with that annotation) — JFR's filter syntax, validated by the agent. Returns
per method: invocations, total, average and maximum time (`jdk.MethodTiming`); the slowest `limit` calls
(`jdk.MethodTrace`, only calls of at least `minMs`) with thread, duration, and an owner-attributed stack; and
`callers`: the distinct calling frames with counts. A trace stops early once it has seen 100 000 calls
(`truncated: true`), so tracing a method that runs a million times a second cannot drown the game.

Both tools also work on clients, are offered in read-only mode (they change nothing), and belong to a new
`debug` tool group (with `client_eval`).

**Rejected.** Our own sampler thread (`Thread.getStackTrace` is safepoint-biased and stops the game thread on
every sample); bundling async-profiler (native, per-platform binaries); a Java agent/ByteBuddy for tracing
(dependency, and permanent instrumentation); Paper's bundled spark (Paper only, not on clients, not ours).

## 2. Bot movement

**Today** `move_to` walks in a straight line and jumps 1-block steps; anything else ends in `stuck`.

**`move_to` finds a path (A\*) and follows it.** `path: false` keeps the straight line.
- The search runs on the server thread over loaded chunks only (an unloaded chunk is a wall; nothing is loaded
  or generated). Limits: 40 000 nodes, and the target within 256 blocks.
  *As built:* when the search runs into unloaded chunks, the bot walks to the closest point it found (up to 64
  blocks), lets the chunks around it load, and searches again.
- A standing node: feet and head without collision (feet may hold a block up to 0.6 high: carpet, slab, snow
  layers, then the head check moves up one), and something to stand on below.
- Moves: the 8 horizontal neighbours (diagonals only when both sides are free), one block up (needs headroom
  for the jump), down up to `maxFall` (default 3) blocks, swimming through water (costlier), climbing ladders,
  vines and scaffolding, and walking through doors and fence gates (`openDoors`, default true; iron doors are
  walls).
- Never: lava, fire, magma, cactus, berry bushes, powder snow, wither roses, campfires.
- Following: the bot steers to the centre of the next node, jumps when the next node is higher or it bumps a
  step, holds jump in water and on ladders, and opens a closed door in its way with a real right-click
  (`PlayerInteractEvent`, so a region plugin can refuse; then `reason: "blocked"`). When it stops making
  progress it searches again from where it stands (at most 3 times), which also handles mobs and players in the
  way.
- Result as today plus `path: {nodes, length}`, `replans`, and new reasons `no_path` (with the closest point
  the search reached; `partial: true` walks there instead) and `blocked`.

**New `bot_action` verbs**, each through the server's own packet handler so plugins see the events a real client
causes:
- `break_block {block, face?}`: mines like a survival player: looks at the block, starts digging, swings every
  tick, and finishes after the block's real dig time for the held tool (instant in creative). Returns `broken`,
  the block, ticks taken, and `cancelled` when a plugin cancelled `BlockBreakEvent` (or `BlockDamageEvent`).
  Out of reach (block interaction range) is an error that says to `move_to` first.
- `jump`; `sneak {on}` (`PlayerToggleSneakEvent`); `sprint {on}` (`PlayerToggleSprintEvent`);
  `drop {all?}` the held item or stack (`PlayerDropItemEvent`); `swap_hands` (`PlayerSwapHandItemsEvent`).
- `state` adds `sneaking`, `sprinting`, `onGround`.

The pathfinder is a pure class over a small block view, unit-tested with hand-built worlds; Paper ITs cover a
maze, steps, drops, a door, water and ladders, and each new verb with its event.

## 3. `client_eval`

**`client_eval {code, timeoutMs 100-60000 (5000), reset?}`** runs JavaScript on the client's render thread, like
`server_eval` on the server. Globals: `mc` (the Minecraft instance), `player`, `level`, `screen()`, `print`, and
`Java.type` for any class, the mods' own included (26.x is unobfuscated, so names are Mojang's).

**GraalJS on the client.** Paper downloads GraalJS through its library loader; Fabric has nothing like it, and
bundling it would make the mod ~60 MB. Decision: the agent downloads it on the first `client_eval` from Maven
Central into `~/.craftwire/lib/graaljs-<version>/`, checks every jar against a sha256 list generated at build time
from the same dependency the Paper plugin uses, and loads it in its own class loader. The script engine code is
shared with Paper (new module `agent-script`); on Fabric it ships inside the agent jar as a nested jar that only
that class loader sees, so the game never loads GraalJS unless `client_eval` is used.
- First call: the hub allows 5 minutes for the download (about 60 MB); later calls start in about a second.
- Turn it off with `-Dcraftwire.allowEval=false` (or `allow-eval=false` in `config/craftwire.properties`).
- Not available in read-only mode.

## 4. MCP resources and prompts

**Resources** (the AI reads them like files, and can subscribe to updates):
- `craftwire://instances`: the connected games and servers (updated on connect/disconnect).
- `craftwire://instances/{instance}/log`: the last 200 log lines (updated as lines arrive, at most once per
  second).
- `craftwire://instances/{instance}/chat`: a client's recent chat and action bar. *As built:* clients only; the
  server's chat is in its log.
- `craftwire://exceptions`: the grouped exceptions.
- `craftwire://instances/{instance}/screenshot`: a PNG taken when read.
- `craftwire://docs/{topic}`: scenarios, extensions, http (shipped in the npm package).

**Prompts** (slash commands in clients that show them), filled with live state (connected instances, plugins):
- `test_plugin {plugin?}`: build, deploy, write scenarios for the plugin's commands and menus, run them, check
  exceptions.
- `debug_lag {instance?}`: profile, find the owner, trace its hot method, propose a fix.
- `write_scenario {feature}`: the scenario format, the server's plugins and commands, then write and run one.
- `setup`: what is connected and what is missing, with the next step.

**MCP registry.** `server.json` (name `io.github.UXPLIMA/craftwire`, the npm package) and `mcpName` in
`package.json`. Publishing needs the owner's GitHub login: prepared and validated here, published only with the
user's go-ahead.
